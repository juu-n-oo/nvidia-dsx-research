NVIDIA Config Manager (nv-config-manager)
구조 · 역할 정리와 AIPub 적용 검토

대상: github.com/NVIDIA/nv-config-manager 상태: Developer Preview 라이선스: Open Source (Apache 2.0)
TL;DR

NVCM(NVIDIA Config Manager)은 대규모 데이터센터 네트워크를 위한 오픈소스 자동화·구성 관리 플랫폼이다. Kubernetes 위에 Helm으로 배포되는 이벤트 기반 마이크로서비스 모노레포다.

  • 핵심 패턴: Nautobot(Source of Truth) → 변경 이벤트 → NATS JetStream → Render(Jinja2) → Config Store(불변 버전 저장). 선언된 의도(intended)로부터 디바이스 설정을 자동 생성·버전관리한다.
  • 7개 서비스: Nautobot · Render · Config Store · ZTP · DHCP · Temporal · UI. 여기에 MCP 서버(AI/LLM 에이전트 연동)가 더해진다.
  • AIPub 적용: NVCM은 네트워크/디바이스 레이어, AIPub은 k8s 플랫폼 레이어 — 레이어는 다르지만 "선언→렌더→불변 저장→승인→재조정" 패턴이 동형이다. 불변 Config Store · Temporal 승인 게이트 · MCP 셀프서비스 세 가지가 차용 후보다.

이 문서의 목적 · NVCM 포지셔닝

이 문서의 목적
NVIDIA가 공개한 nv-config-manager(NVCM)가 어떻게 구성되어 있고 어떤 역할을 하는지 정확히 파악하고, 그 설계 패턴 중 AIPub k8s 플랫폼에 적용 가능한 것을 도출한다.

NVCM은 스위치·디바이스의 "구성 파일(config)"을 인벤토리로부터 생성·배포·버전관리하는 레이어에서 동작한다. 물리 fabric·DPU 인프라를 직접 제어하는 하위 레이어가 아니라, 그 위에서 네트워크 디바이스 구성을 자동화하는 상위 레이어다.

NVCM 개요

NVCM은 스스로를 "대규모 데이터센터 운영을 위한 오픈소스 네트워크 자동화·구성 관리 플랫폼"이라 정의한다. 스위치 인프라 전반의 구성과 프로비저닝을 통합해 수작업 구성 워크플로를 제거하고 Infrastructure-as-Code 방식을 가능하게 한다.

어떤 문제를 푸는가

  • 단일 진실 공급원(SoT): 디바이스·IP·케이블·인벤토리를 Nautobot 한 곳에서 관리한다.
  • 선언 → 자동 렌더: SoT가 바뀌면 이벤트가 발생하고, 템플릿으로 디바이스별 config를 자동 생성한다(수작업 CLI 제거).
  • Zero-Touch 프로비저닝: 새 스위치가 네트워크에 붙으면 DHCP→ZTP로 부팅 스크립트·OS 이미지·설정을 자동 전달한다(Day-0).
  • 변경 워크플로 + 승인 게이트: 운영 중(Day-2) 변경은 Temporal 워크플로로 오케스트레이션하고, 사람 승인·감사 추적을 남긴다.
  • 불변 이력·롤백: 렌더된 config를 버전별 불변 저장, diff·감사·롤백을 지원한다.
주의 — Developer Preview
공식 문서는 현재 프로덕션 사용을 권장하지 않는다. API·스키마가 변할 수 있으므로 AIPub 적용 시에는 "패턴을 차용" 관점으로 접근하는 것이 안전하다.

아키텍처 — 이벤트 기반 마이크로서비스

NVCM은 하나의 모노레포에서 여러 전문 서비스가 NATS JetStream 이벤트 브로커를 중심으로 느슨하게 결합된 구조다. 상태는 PostgreSQL(Config Store)과 Redis(캐시·분산 락)에 저장되고, 모든 진실의 근원은 Nautobot이다.

이벤트 기반 데이터 흐름 — 렌더 파이프라인

NVCM의 심장부는 Render 서비스다. 스스로를 "네트워크 디바이스 구성을 자동 생성·버전관리하는 이벤트 기반 마이크로서비스"로 정의하며, NATS JetStream에서 3종의 pull 컨슈머로 이벤트를 소비한다.

렌더 흐름 — 수동 트리거(POST /v1/render/{uuid}/render · /all · /batch)도 동일 파이프라인 사용

흐름의 핵심 특징

  • 동적 이벤트 라우팅: events/ 모듈을 introspection하여 Nautobot 모델 이벤트를 핸들러 함수에 자동 매핑(수동 등록 불필요).
  • 분산 락: Redis 기반 락으로 다수 컨슈머 인스턴스가 같은 디바이스를 동시에 렌더하지 못하게 막는다.
  • 무중단 롤링 배포: Template Producer(배포 시 Kubernetes Job)가 stale 템플릿 버전 디바이스를 찾아 재렌더 이벤트를 발행. 더 새로운 템플릿 버전은 30초 지연 NAK으로 거부해 롤링 중 충돌 방지.
  • 관측성: 이벤트 수신·처리·실패·처리시간, end-to-end 지연을 Prometheus 메트릭으로 노출.
  • 재조정 방식: NVCM은 주기적 reconcile이 아니라 이벤트 기반 반응형이다(변경 발생 시에만 렌더). — 이 점이 controller-runtime 기반 AIPub과의 중요한 차이다(뒤 AIPub 절 참고).

서비스별 역할 상세

Nautobot
Django · GraphQL · SoT

네트워크 단일 진실 공급원. 디바이스·IP·케이블·인벤토리 관리 + 모델 변경 시 이벤트 발행. 커스텀 Job 실행. nautobot-app-overlays로 InfiniBand mkey/pkey·VXLAN 오버레이 모델링.

Render
Python · Jinja2 · NATS

이벤트를 소비해 Nautobot 데이터 + Jinja2 템플릿으로 디바이스별 config를 생성. 3종 pull 컨슈머 + 동적 dispatch + Redis 락. 결과를 Config Store에 저장.

Config Store
Python · FastAPI · PostgreSQL

렌더된 config를 불변 버전으로 영속화. intended/backup 타입, 버전 자동 증가(v1~), SHA256 dedup, 버전간 diff, 1년 보관. Redis 캐시 + cache refresh service.

ZTP
Python · S3 / SFTP

Zero-Touch Provisioning. 새 디바이스에 부팅 스크립트·OS 이미지·설정을 전달하고 프로비저닝 상태를 갱신. 저장 백엔드로 S3·SFTP·filestore 지원.

DHCP
Python · Kea · Redis

Nautobot 인벤토리로부터 Kea DHCP 구성을 생성(kea_dhcp_confgen.py). ZTP 부팅을 위한 IP·부팅 정보 제공. GraphQL 조회 + 메트릭.

Temporal
Temporal · Worker

장기 실행 작업·승인 게이트 워크플로 오케스트레이션. UI와 백엔드 서비스 간 조정. deploy·backup·비밀번호 로테이션 등 다수 내장 워크플로.

UI
React · Next.js

관리용 웹 인터페이스. 렌더·배포·워크플로·승인·이력 조회. 로컬 config-manager.local 엔드포인트로 접근.

MCP Server
Model Context Protocol

NVCM을 AI/LLM 에이전트에 노출하는 MCP 서버(src/nv_config_manager/mcp). OAuth proxy·tools·workflows. 자연어로 플랫폼을 조회·조작하는 진입점.

AIPub 적용 방안

레이어 경계 — 핵심 전제
NVCM은 네트워크 디바이스/스위치 구성 레이어에서 동작하고, AIPub은 그 위 resource-group-controller 중심의 k8s 플랫폼 레이어에서 동작한다. NVCM을 그대로 이식하는 것이 아니라, 설계 패턴을 차용하는 관점이 옳다.

구조적 동형성 (Isomorphism)

레이어는 다르지만 두 시스템 모두 "선언된 의도 → 렌더/조정 → 저장 → 승인 → 관측"이라는 동일한 골격을 가진다.

단일 진실 공급원Nautobot (인벤토리·IP·케이블)Project CR spec (+ etcd)

NVCM 3대 패턴 → AIPub k8s 플랫폼 레이어 차용안

구체적 제안

1. 불변 렌더 이력 저장소 (Config Store 패턴)

AIPub의 resource-group-controller는 현재 k8s API에 현재 상태만 apply한다. NVCM Config Store처럼 reconcile가 생성한 manifest 묶음을 불변 버전으로 스냅샷 저장하면, "누가·언제·무엇을" 감사하고 특정 버전으로 롤백할 수 있다. SHA256 dedup·버전간 diff는 그대로 차용 가능한 설계다.

status:
  renderedRevision: 42                 # 불변 버전 번호
  contentHash: sha256:9f3c…            # dedup용 해시
  history:
    - rev: 41, author: alice, ts: 2026-07-01T10:20Z, msg: "quota 16→24"
  drift: [Unexpected | Stale | Missing | Intentional]   # intended vs actual

2. 민감 작업 승인 게이트 (Temporal 워크플로 패턴)

NVCM은 디바이스 배포 같은 위험 작업을 Temporal 워크플로로 감싸 사람 승인을 강제한다. AIPub도 ResourceQuota 대폭 증설·Project 삭제·클러스터 리소스 회수 같은 작업에 승인 게이트를 두면 안전하다. k8s 환경이므로 Temporal 대신 Argo Workflows나 admission webhook 기반 승인 CRD로도 구현 가능하다.

3. MCP 셀프서비스 (MCP 서버 패턴)

NVCM은 MCP 서버로 플랫폼을 LLM 에이전트에 노출한다. "AIPub"이라는 이름·목적과 가장 잘 맞는 차용안이다. AIPub MCP 서버를 두면 사용자가 자연어("team-alpha에 GPU 4장짜리 프로젝트 만들어줘")로 Project CR을 생성·조회하는 셀프서비스가 된다. 기존 Spring Boot aipub-backend API를 MCP tool로 감싸는 형태가 현실적이다.

보너스 — SoT + 이벤트 렌더 발상

NVCM의 "Nautobot(SoT) → 이벤트 → 템플릿 렌더" 파이프라인은, AIPub이 여러 k8s 리소스를 하나의 상위 의도(Project)로부터 템플릿 렌더링하는 발상으로 옮길 수 있다. 즉 Project를 "템플릿 + 값"으로 보고 Namespace·RBAC·Quota·NetworkPolicy를 일관 렌더. 단, 트리거는 NVCM의 반응형이 아니라 AIPub의 controller-runtime 재조정 루프를 유지하는 것이 k8s 관례에 맞다.

적용 시 유의
NVCM은 디바이스 config 파일(텍스트)을 다루므로 "불변 버전+diff"가 자연스럽다. AIPub은 살아있는 k8s 객체를 다루므로, 저장소는 "선언 의도의 이력"과 "reconcile 결과 스냅샷"을 저장하는 보조 축으로 두고, 진실의 근원은 여전히 etcd/CR로 유지해야 한다.

정리 · 시사점

  • NVCM은 오픈소스 네트워크 자동화·구성 관리 플랫폼(Developer Preview)이며, 역할은 "대규모 데이터센터 네트워크 디바이스의 구성 자동화·버전관리"다.
  • 설계의 요체: SoT(Nautobot) → 이벤트(NATS) → 렌더(Jinja2) → 불변 저장(Config Store) → 승인 워크플로(Temporal), 그리고 MCP로 AI 연동. 각 축이 독립 서비스로 분리되어 있다.
  • AIPub 차용 3선: ① 불변 렌더 이력 저장소, ② 민감 작업 승인 게이트, ③ MCP 셀프서비스. 셋 다 감사·롤백·안전성·셀프서비스를 강화한다.
  • 경계 유지: 레이어(네트워크 vs k8s 플랫폼)와 트리거 모델(반응형 vs 재조정형)의 차이를 지키면서 "패턴"만 이식하는 것이 안전하다.
