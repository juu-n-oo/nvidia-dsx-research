NVIDIA DSX OS
AI Factory Network Configuration Management

111 에이전트 · 28 소스 · 130 클레임 추출 · 25 검증 → 16 확인 / 9 기각
TL;DR

NVIDIA DSX OS 네트워크 구성 관리는 단일 시스템이 아닌 fabric별 전문 컴포넌트 계층이다.

  • NICo: Ethernet은 DPU Agent pull-push(30초), InfiniBand/NVLink는 Monitor 태스크 → 외부 API 교정 — 이원화 패턴 코드 레벨 확인
  • DPF: Host Cluster + DPU Cluster 이중 k8s 아키텍처, DPUService 5종 CRD, ArgoCD-as-Helm-engine으로 DPU 클러스터에 간접 reconcile
  • AIPub 적용: 물리 fabric(NICo/DPF)과 k8s 플랫폼(AIPub) 레이어를 명확히 분리; resource-group-controller reconcile을 NetworkPolicy/CNI로 확장하는 것이 현실적인 경로

선수 배경지식

이 리포트를 읽기 위해 필요한 개념들을 간략히 정리한다.

Desired-state / Reconcile 루프

쿠버네티스의 핵심 패턴: 사용자는 원하는 상태(spec)를 선언하고, 컨트롤러는 현재 상태(status)와 지속적으로 비교해 차이를 줄인다. desired ≠ actual → 교정, desired == actual → 대기. NICo·DPF 모두 이 패턴을 구현한다.

Drift (구성 표류)

선언된 desired state와 실제 운영 상태가 시간이 지나면서 달라지는 현상. 원인: 수동 변경, 외부 자동화, 하드웨어 장애, 오퍼레이터 버그. Drift 감지 → 분류(의도적/비의도적) → 교정이 Day-2 운영의 핵심 과제다.

DPU (Data Processing Unit)

NVIDIA BlueField는 CPU에서 네트워킹·스토리지·보안 처리를 offload하는 SmartNIC. 호스트와 독립적인 ARM 코어와 OS를 가지며, DPU 위에서 격리된 소프트웨어를 실행할 수 있다. 이를 통해 테넌트 간 하드웨어 레벨 격리가 가능하다.

HBN (Host-Based Networking)

BlueField DPU의 네트워크 스택. DPU 위에서 OVS(Open vSwitch) 기반 L2/L3 forwarding을 수행해 호스트 네트워크 구성을 소프트웨어적으로 제어한다.

ArgoCD와 GitOps

ArgoCD는 Git 저장소(또는 Helm 차트)를 source-of-truth로 삼아 k8s 클러스터 상태를 지속 reconcile하는 GitOps 도구. DPF는 ArgoCD를 Git source-of-truth 방식이 아닌 Helm-as-engine 방식으로 사용한다 — ArgoCD Application 객체를 프로그래밍으로 생성해 Helm chart 설치를 간접 실행한다.

Kamaji

Control plane-as-a-service: 다수의 k8s 컨트롤 플레인을 management 클러스터 내 Pod으로 실행. DPF는 Kamaji TenantControlPlane 객체로 DPU 클러스터의 API server·etcd를 프로비저닝한다.

DSX OS 개요

DSX OS는 NVIDIA AI Factory를 운영하는 오픈소스 모듈형 소프트웨어 스택이다. 단일 제품이 아니라 독립적인 GitHub 저장소들의 집합이며, 각 컴포넌트는 명확히 분리된 책임을 가진다.

패턴 1: InfiniBand + NVLink — Monitor 태스크 기반

NICo Core
  ├─ IbFabricMonitor  (주기적 실행)
  │    └─ expected partition/pkey vs actual (UFM API 조회)
  │         └─ mismatch → UFM REST API 호출로 교정
  │
  └─ NvlPartitionMonitor  (주기적 실행)
       └─ expected NVLink partition vs actual (NVLink Manager 조회)
            └─ mismatch → NVLink Manager API 호출로 교정

패턴 2: DPU 관리 Ethernet — DPU Agent pull-push

NICo Core  ←──gRPC──→  DPU Agent (BlueField 위에서 실행)
              ↑                    ↓
  RecordDpuNetworkStatus  GetManagedHostNetworkConfig
  (observed state 보고)   (desired config 30초마다 폴링)
                                   ↓
                          HBN (Host-Based Networking) 적용
                                   ↓
                          스위치/OVS 구성 변경

DPU Agent는 30초마다 NICo에 desired config를 폴링하고, HBN에 적용한 뒤, observed state를 gRPC로 다시 보고한다. 이것이 NICo의 Ethernet 레이어 reconcile 루프다.

Helm 배포 구조

NICo는 Helm 3-레이어로 배포된다: common-services → nico-core → nico-services. k8s 위에 배포되지만 k8s-native microservices suite는 아니다 — Rust 단일 바이너리 기반이며 k8s는 실행 환경으로 사용한다.

기각된 클레임 (0-3)
"NICo는 k8s-native 마이크로서비스 suite이며 모든 서비스가 mTLS/gRPC로 통신한다" — 기각. NICo는 Rust 단일 바이너리에 더 가까우며, k8s-native suite 주장은 소스에서 뒷받침되지 않는다.

AI Factory 네트워크 구성 관리 Lifecycle

Day-0
부트스트랩 + 케이블링 검증
  • CVT (Cable Validation Tool)로 물리 케이블링 검증 — topology 파일이 source-of-truth
  • Drift 분류: Wrong-neighbor / Wrong-port / Unknown-neighbor / Extra-cable
  • NVUE로 초기 스위치 구성 파일 적용 (nv config apply)
  • DPF: DPUSet + BFB + DPUFlavor 선언 → DPU 프로비저닝 시작
  • NICo: 호스트·DPU 등록, 초기 partition/pkey 설정
Day-1
프로비저닝 + 설정 적용
  • UFM: InfiniBand fabric 자동 발견, partition/pkey 프로비저닝
  • NVUE: 선언적 구성 트리 적용 (4-state: Pending→Applied)
  • NMX-C: NVLink 초기 파티션 설정, nvlSM + GFM 활성화
  • DPF: DPUService CRD → ArgoCD → DPU 클러스터 Helm 설치
  • DPUServiceInterface/Chain → OVS 포트·플로우 프로그래밍
Day-2
운영 + Drift 감지 + 업그레이드
  • NICo IbFabricMonitor: IB drift 주기 감지 → UFM API 교정
  • NICo NvlPartitionMonitor: NVLink drift → NVLink Manager API 교정
  • NICo DPU Agent: 30초 Ethernet reconcile 루프 지속
  • NetQ snapshot-compare: 상태 변경 감지 및 색상 분류
  • NMX 폐루프: NMX-T → NMX-M → NMX-C 자동 교정
  • fleet-intelligence-agent: 지속 텔레메트리 수집

Fabric별 구성 관리 모델 심층

Spectrum-X Ethernet
NVUE + NetQ + NICo DPU Agent

NVUE 4-state 모델: Pending → Applied → Operational → Startup. 전체 Cumulus Linux 구성을 단일 트리로 선언. nv config diff <state1> <state2>로 임의 두 상태 비교.

NetQ 검증: BGP(7개 테스트), EVPN, 인터페이스, MTU, RoCE, 토폴로지, VLAN, VxLAN 등 14+ validation 체크. Snapshot 비교: added(green)/removed(red)/modified(orange) 색상 분류.

InfiniBand (Quantum)
UFM + NICo IbFabricMonitor

DPU 기반 격리는 하드웨어 레벨에서 강제된다: 테넌트 A의 트래픽은 DPU의 OVS 포트/플로우 규칙에 의해 물리적으로 분리된다. 소프트웨어 정책이 아닌 데이터 경로 자체를 분리.

기각된 클레임 (0-3)
"NICo가 leaf switch를 재구성하지 않는다" — 기각. 실제로 NICo는 Ethernet 레이어에서 스위치 구성에 관여하며, "underlay는 static"이라는 주장은 소스에서 뒷받침되지 않는다.

AIPub 적용 방안

레이어 경계 — 핵심 전제
NVIDIA (NICo/DPF)는 물리 fabric/DPU 인프라 레이어를 담당한다. AIPub (resource-group-controller)는 그 위 k8s 플랫폼 레이어에서 동작한다. AIPub이 물리 fabric을 직접 제어하지 않는다 — 이 경계를 지켜야 설계가 올바르다.

구조적 동형성 (Isomorphism)

NICo와 AIPub resource-group-controller는 구조적으로 동일한 패턴을 다른 레이어에서 구현하고 있다:

개념NICo/DPF (인프라 레이어)AIPub resource-group-controller (플랫폼 레이어)
Desired state 선언NICo API에 host/partition 등록, DPUSet CRResourceGroup / Project CR spec
Observed state 수집DPU Agent gRPC 보고, Monitor 태스크 조회k8s API 조회 (Namespace/RBAC/NetworkPolicy 현재 상태)
Diff 계산expected vs actual 비교server-side apply dry-run → managed fields diff
Reconcile 실행HBN 적용, UFM/NVLink API 호출controller-runtime reconcile loop
정책 강제DPU 하드웨어 레벨admission webhook + NetworkPolicy
텔레메트리 분리fleet-intelligence-agent (읽기 전용)별도 상태 수집기 (제안)

구체적 확장 방안

1. ResourceGroup CR에 NetworkPolicy 선언 추가

apiVersion: aipub.ten1010.io/v1alpha1
kind: ResourceGroup
metadata:
  name: team-alpha-project
spec:
  # 기존 필드들 (Namespace, RBAC, ResourceQuota)
  namespaceTemplate:
    labels: { ... }
  resourceQuota:
    requests.cpu: "16"

  # 추가: 네트워크 격리 정책 선언
  networkPolicy:
    isolationLevel: strict        # none | strict | custom
    egressRules:
      - to: [{ namespaceSelector: { matchLabels: { tier: shared } } }]
    ingressRules:
      - from: [{ podSelector: {} }]   # 같은 namespace 내부만
    bandwidthAnnotations:
      kubernetes.io/ingress-bandwidth: "1G"
      kubernetes.io/egress-bandwidth: "1G"

2. Reconcile Loop 확장 (controller-runtime)

ResourceGroup CR 변경 (spec.networkPolicy)
         ↓
resource-group-controller reconcile loop
         ↓
  [기존] Namespace, RoleBinding, ResourceQuota reconcile
         ↓
  [신규] NetworkPolicy reconcile
    - server-side apply dry-run → desired-vs-actual diff 계산
    - diff가 있으면: NetworkPolicy apply (또는 patch)
    - diff 없으면: 대기
         ↓
  [신규] CNI annotations (bandwidth limits)
    - Pod에 bandwidth annotation 주입 (admission webhook)
         ↓
  status 업데이트
    - networkPolicyStatus: { applied: [...], drift: [...] }

3. Server-side Apply Dry-run으로 Diff 가시화

// controller-runtime에서 dry-run diff 예시
patchOptions := &client.PatchOptions{
    DryRun:       []string{metav1.DryRunAll},
    FieldManager: "aipub-resource-group-controller",
}
err := r.Client.Patch(ctx, desiredNetworkPolicy,
    client.Apply, patchOptions)

// 응답 객체의 managed fields로 drift 분류:
// - .metadata.managedFields → 마지막 적용자/시간
// - 현재 리소스와 dry-run 결과 비교 → 변경될 필드 목록 추출

4. Drift 분류 체계 (CVT 패턴 차용)

분류의미교정 방침
UnexpectedResourceGroup CR에 없는 NetworkPolicy가 존재삭제 (garbage collect)
Stale이전 버전 정책이 남아 있음교체 (apply)
MissingCR spec에 있는 정책이 없음생성
Intentional주석(aipub.io/drift-ignore)으로 표시된 차이무시

5. Admission Webhook으로 정책 강제

resource-group-controller의 기존 webhook을 확장해 Pod 생성 시 NetworkPolicy 존재를 검증하고, bandwidth annotation을 자동 주입한다. NICo의 "expected state 선언 → 위반 시 교정" 패턴과 동일한 구조를 admission 계층에서 구현.

우선순위 로드맵

단계작업의존성
1단계 ResourceGroup CR에 spec.networkPolicy 필드 추가 + NetworkPolicy reconcile CNI 설치 (Calico/Cilium), 기존 controller-runtime reconcile 구조
2단계 server-side apply dry-run 기반 drift 감지 + status 보고 1단계
3단계 분류된 drift report (Unexpected/Stale/Missing) API 노출 2단계
4단계 bandwidth annotation webhook, QoS 선언 지원 CNI bandwidth plugin (community edition 이상)
medium
AIPub resource-group-controller의 기존 reconcile 패턴을 NetworkPolicy/CNI로 확장하는 것이 현실적인 경로. 물리 fabric(NICo/DPF 담당)은 건드리지 않는다.
이 finding은 확인된 NVIDIA 클레임에서 도출한 설계 추론. 실제 AIPub 코드베이스 코드 수준 검토 후 타당성 재확인 필요. (confidence: medium)

미해결 질문

  1. NICo IbFabricMonitor/NvlPartitionMonitor가 외부 fabric 관리자(UFM, NVLink Manager)에 교정 API 호출을 할 때, 교정 실패·부분 성공·타임아웃 시나리오를 어떻게 처리하는가? 재시도 정책과 backoff 전략이 코드에 구현되어 있는가?
  2. DPF DPUCluster(Kamaji 기반)와 DPU 위 DOCA 서비스 간 네트워크 격리가 멀티테넌트 시나리오에서 구체적으로 어떻게 강제되는가? OVS 기반 격리가 테넌트 간 트래픽 누출을 하드웨어 레벨에서 차단하는지 검증된 소스가 있는가?
  3. fleet-intelligence-agent가 수집한 InfiniBand 텔레메트리(포트 카운터, 링크 헬스)가 NICo IbFabricMonitor 등 다른 컴포넌트와 연동되는가? 텔레메트리 데이터가 자동 교정 루프에 피드백되는 경로가 존재하는가?
  4. AIPub resource-group-controller에서 NetworkPolicy를 ResourceGroup CR spec으로 선언할 때, Calico/Cilium 등 CNI별 호환성 — 특히 멀티테넌트 Workspace 간 QoS/bandwidth 제한 선언 CRD 설계 — 에서 선택해야 할 구체적 구현 패턴은 무엇인가?
