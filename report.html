NVIDIA DSX의 구성 관리 패턴과 AIPub 적용

NVIDIA가 AI Factory 물리 인프라에서 구현한 “기준 정보 → drift 감지 → reconcile” 모델을 해부하고, 그 운영 패턴을 쿠버네티스 기반 ML 플랫폼 AIPub으로 어떻게 끌어올지 정리한다. 더불어 이 주제를 읽기 위한 선수 배경지식을 함께 싣는다.

01 — 요약

핵심 결론

세 문장으로 줄이면 이렇다.

  • DSX는 단일 OS가 아니다. AI Factory를 설계·시뮬레이션·구축·운영하는 풀스택 프레임워크이고, DSX OS는 그중 운영 담당 오픈소스 모듈이다. 전부 물리/인프라 레이어로, AIPub이 위치한 ML 플랫폼 레이어보다 아래다.
  • NVIDIA의 구성 관리 도구는 “선언적 기준정보 + diff 기반 drift 감지”를 일관되게 구현한다. 다만 대부분은 감지까지이고, 자동 교정(reconcile) 루프는 NMX-M→NMX-C와 일부 클라우드 사업자(Oracle OCI) 구현에서만 확인된다.
  • 이 패턴은 사실 쿠버네티스 오퍼레이터의 네이티브 모델이다. AIPub은 이미 resource-group-controller로 reconcile 루프를 갖고 있으므로, NVIDIA의 fabric 툴을 재구현할 게 아니라 그들이 검증한 운영 UX 패턴을 끌어오면 된다.

02 — 가장 먼저 바로잡을 것

“NVIDIA Config Manager (MVCM)”의 실체

정정

리서치 출발점의 가설 명칭 “NVIDIA Config Manager (MVCM)”는 실제 NVIDIA 제품명으로 확인되지 않았다. 다중 소스 검증 결과 그런 단일 제품은 존재하지 않는다.

실제 fabric/구성 관리 주체는 fabric 종류별로 분리된 5개다. 설계 문서·티켓에는 반드시 아래 실명을 쓰고, 가상의 “MVCM”에 의존하지 않는다.

03 — 대상 파악

DSX란 무엇인가

DSX는 단일 제품도 OS도 아닌 풀스택 프레임워크/포트폴리오다. 칩·시스템·네트워크(Spectrum-X/InfiniBand/NVLink)·스토리지·전력·시설·파트너 기술까지 “AI Factory를 어떻게 짓고 최적화하는가”를 정의한다(2026-06 발표). 구성요소는 참조 설계(DSX Reference Design), 디지털 트윈(Omniverse DSX Sim), 운영 레이어(DSX OS), 전력·인프라 계열(MaxLPS/Flex) 등으로 나뉜다.

DSX OS

DSX의 운영 담당 오픈소스 모듈 소프트웨어다. lifecycle management, intelligent scheduling, runtime consistency, health automation, resiliency, multi-tenant operations를 제공한다고 명시한다. 일부는 실제 공개 레포(NVIDIA/infra-controller-core, NVIDIA/doca-platform 등)로 릴리스됐는데, 이것이 마케팅이 아닌 가장 강한 신호다.

레이어 경계 — 이 문서 전체의 전제

DSX OS조차 “모델을 운영”하는 게 아니라 “factory(물리 인프라)를 운영”한다. AIPub은 그 위 ML 애플리케이션/플랫폼 레이어다. AIPub은 ten1010 클러스터/네트워크를 연동·표시할 수는 있어도 소유·제어하지 않는다 — 이 선이 적용안의 출발점이다.

04 — 메커니즘

구성 관리 5종과 desired-state / drift / reconcile

요청서의 “MVCM” 대신, 아래 실재 도구들이 공통적으로 기준 정보(source-of-truth) → 실제 상태 diff → drift 분류 → (일부) 교정 패턴을 구현한다.

NMX — 자동 교정에 가장 가까운 폐루프

NVLink fabric용. 텔레메트리→분석→제어의 닫힌 루프로, NVIDIA 스택 내에서 “drift 감지 → 자동 교정”에 가장 근접한 구조이며 AIPub reconcile 컨트롤러의 직접적 개념 템플릿이다.

NMX-T
Telemetry

수집·집계·전송

NMX-M
Manager

ML 추론으로 패턴 감지 → 구성 변경 결정

NMX-C
Controller

nvlSM·GFM 구동, 실제 구성 enact

Oasis
Data lake

이력 저장

NVUE — 진짜 선언적 desired-state 모델

NVIDIA 스택에서 쿠버네티스식 선언적 config에 가장 가깝고, AIPub에 가장 직접 전이 가능한 모델. 객체지향·스키마 구동 트리로 desired config를 nv set으로 선언하고, 상태를 네 가지로 분리한다.

  • Pending — 미커밋(= 의도된 변경)
  • Applied — 커밋됨
  • Operational — 실제 running 상태
  • Startup — 영속화(/etc/nvue.d/startup.yaml)

nv config diff로 임의 두 상태를 비교해 의도 vs 실제 차이(drift)를 표면화한다.

UFM · NetQ · CVT — 검증과 분류된 drift

  • UFM(InfiniBand): 자동 디스커버리 + 13개 validation tests, system/performance 검증.
  • NetQ(Ethernet): snapshot-and-compare(변경 전/후 diff), preventive validation(NVIDIA Air 디지털 트윈 + CI/CD), 실제 토폴로지를 blueprint 파일과 비교.
  • CVT(케이블링): 토폴로지 파일이 “authoritative source”. drift를 Wrong-neighbor / Wrong-port / Unknown-neighbor / Extra-cable로 분류 — 단 감지 전용, 자동 교정은 안 함.

감지 ≠ 교정

CVT·NetQ snapshot-compare·NVUE diff·UFM validation은 drift 감지/diff까지다. 닫힌 자동 reconcile 루프는 NMX-M→NMX-C와 Oracle OCI 사례에서만 확인된다. “diff 기능”과 “reconcile 루프”를 혼동하지 말 것. (OCI를 “완전한 선언적 IaC”로 규정하는 두 강한 주장은 검증에서 refuted 1-2.)

05 — 핵심

AIPub 적용

결론부터. NVIDIA의 fabric 툴(NMX/UFM/CVT/NVUE)을 재구현하지 않는다. 그들이 검증한 제어 패턴과 운영 UX만 빌려 AIPub 레이어 자원(리소스 그룹/쿼터/RBAC/정책/레지스트리)에 적용한다. 그 패턴은 사실 쿠버네티스 오퍼레이터의 네이티브 모델이므로, resource-group-controller로 이미 절반은 와 있다.

패턴 매핑

NVIDIA 자산핵심 아이디어AIPub 전이
NVUE 4-state + config diff의도(spec)와 실제(running)를 상태로 분리·비교리소스 그룹/쿼터/정책의 desired vs observed diff 뷰 + apply 전 미리보기
NMX-M→C, OCI reconciledrift 지속 감지 + 자동 교정오퍼레이터 reconcile이 drift 감지 → 자동 교정 또는 알림
CVT 분류된 driftsource-of-truth 대비 이산·actionable 분류“expected vs actual” 리포트 — 누락 namespace, 쿼터 불일치, RBAC divergence 등
DSX Sim / NetQ+Air프로덕션 전 모델에서 변경 검증변경 적용 전 dry-run·영향 시뮬레이션
UFM 13 tests표준 validation 체크 집합리소스 그룹 표준 정합성 체크 묶음

현황과 gap

resource-group-controller는 이미 Project/AipubUser/NodeGroup/ImageHub CR을 reconcile하며 파생 리소스(Namespace/RBAC/Quota/Secret/webhook)를 정합한다. 즉 핵심 루프는 존재한다. 빠져 있을 가능성이 큰 부분(코드 재확인 필요):

  • 사용자 노출 desired-vs-observed diff UI가 없음 (NVUE diff / CVT 리포트에 해당)
  • apply 전 dry-run/시뮬레이션 게이트가 없음 (DSX Sim에 해당)
  • drift의 명시적 분류·리포팅이 없음 (조용히 교정될 뿐 감사 자취가 안 남음)
  • 교정 vs 알림 정책 선택지가 불명확

단계별 도입 — 감지 먼저, 교정은 신중히

desired vs observed를 status/프론트에 노출, CVT식 카테고리 분류 (위험 0)

Phase 2

Phase 4

멀티클러스터/감사 요구 시에만 외부 source-of-truth

안티패턴

① NVIDIA fabric 툴 재구현 ② “MVCM” 가상 명칭에 의존 ③ k8s가 이미 주는 것(reconcile/diff/dry-run/webhook) 평행 구현 ④ 감지를 곧장 자동 교정으로 ⑤ 물리 인프라 제어 주장 — 모두 피한다.

06 — 선수 배경지식

이 주제를 읽기 위한 배경지식

위 내용을 온전히 이해하려면 크게 세 묶음의 사전 지식이 필요하다 — (A) 구성 관리·선언적 모델의 일반 개념, (B) 쿠버네티스 오퍼레이터 메커니즘, (C) 데이터센터 네트워크/AI Factory 인프라 용어. 모르는 카드만 골라 읽으면 된다.

A. 구성 관리 · 선언적 모델

개념

선언적 vs 명령적

명령적(imperative)은 “이 명령들을 실행하라”, 선언적(declarative)은 “최종 상태가 이래야 한다”를 기술하고 시스템이 도달 방법을 알아서 찾는다.

왜 중요NVUE·k8s·AIPub CR이 전부 선언적. 이 글의 모든 패턴의 토대.

개념

Source of truth · Desired state

“있어야 할 상태”를 담은 권위 있는 원본. CVT의 토폴로지 파일, NVUE의 pending config, k8s의 CR spec이 모두 이것.

왜 중요모든 비교(diff)의 기준점.

개념

Drift

실제 상태가 선언된 상태에서 벗어난 정도. 누가 수동으로 바꿨거나, 장애·부분 적용으로 발생. drift 감지 = 의도와 실제의 diff.

왜 중요NVIDIA 도구 5종이 공통으로 하는 일.

개념

Reconcile · Idempotency

desired와 actual을 비교해 간극을 메우는 동작이 reconcile. 같은 입력에 몇 번 돌려도 결과가 같은 성질이 idempotency로, 안전한 반복 적용의 전제.

왜 중요“감지”와 “교정”을 가르는 지점.

실무

GitOps · IaC

Infrastructure as Code = 인프라를 코드로 선언. GitOps는 Git을 source-of-truth로 두고 ArgoCD/Flux가 drift를 감지·동기화하는 방식.

왜 중요Phase 4 옵션의 배경.

B. 쿠버네티스 오퍼레이터

k8s

CRD / CR

CRD는 새 리소스 “종류”를 k8s에 등록하는 스키마, CR은 그 인스턴스. AIPub의 Project·Workspace 등이 CR.

왜 중요AIPub의 desired state가 사는 곳.

k8s

Controller · Reconcile loop

CR(spec=의도)을 watch해서 실제 클러스터(status=현실)와 비교하고 간극을 좁히는 무한 루프. 오퍼레이터 = 도메인 지식을 담은 컨트롤러.

왜 중요resource-group-controller가 바로 이것. NMX 루프와 같은 모양.

k8s

spec vs status

CR의 spec은 사용자가 선언한 의도, status는 컨트롤러가 기록한 관측된 현실. 둘의 차이가 곧 drift.

왜 중요NVUE 4-state와 1:1 대응.

k8s

Admission webhook · dry-run

리소스가 저장되기 전 가로채 검증(validating)/변형(mutating)하는 훅. server-side apply --dry-run은 실제 적용 없이 결과를 미리 계산.

왜 중요Phase 2 “적용 전 검증”의 네이티브 수단.

k8s

RBAC · ResourceQuota · Namespace

각각 권한, 자원 상한, 격리 경계. AIPub 리소스 그룹이 reconcile로 만들어내는 파생 리소스들.

왜 중요drift 분류 카테고리의 대상.

C. 데이터센터 네트워크 · AI Factory

인프라

AI Factory · DGX / SuperPOD

대규모 GPU 학습 전용 데이터센터를 “AI 공장”으로 부른다. DGX는 NVIDIA GPU 서버, SuperPOD는 그 군집 참조 설계.

왜 중요DSX가 다루는 대상 그 자체.

네트워크

Fabric: NVLink · InfiniBand · Ethernet

fabric = 노드를 잇는 고속 상호연결망. NVLink는 GPU 간(노드 내·랙 내), InfiniBand/Spectrum-X Ethernet은 노드 간. 도구가 fabric별로 갈리는 이유.

왜 중요NMX/UFM/NVUE가 나뉘는 근거.

네트워크

SDN · Subnet/Fabric Manager

SDN은 제어를 소프트웨어 컨트롤 플레인으로 분리. Subnet Manager(IB)·GFM(NVLink)은 fabric의 경로·구성을 관장하는 두뇌.

왜 중요NMX-C가 구동하는 것.

네트워크

토폴로지 · 케이블링 검증

스위치·노드 연결 구조가 토폴로지(예: spine-leaf). 수천 가닥 케이블이 설계도대로 꽂혔는지 확인하는 게 케이블링 검증.

왜 중요CVT의 “기준→diff→분류” 사례.

운영

Telemetry · 디지털 트윈

장비가 내보내는 측정 데이터가 telemetry. 디지털 트윈은 실물의 정확한 가상 복제로, 바꾸기 전 시뮬레이션에 쓴다.

왜 중요NMX-T 수집과 DSX Sim의 토대.

한 줄로

핵심 한 가지만 기억한다면 — “선언된 의도(desired)와 관측된 현실(actual)의 diff를 지속적으로 좁힌다”는 reconcile 사고방식이다. NVIDIA가 물리 fabric에서 한 것을, AIPub은 k8s 리소스에서 한다.
